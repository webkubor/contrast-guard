# 页面视觉评审（UI Review）

## 为什么需要这个 skill

「丑」是感受层，agent 的输入是判据层，中间缺翻译器。用户说「这页丑」，agent 只能在
CSS 里随机漂移——这是所有「AI 指导不动 UI」的直接原因。

更麻烦的是：**丑的每一处单看往往都"对"**。每个色值都是合法 token，每个圆角都在白名单里，
但一屏 9 种字号、灰阶只拉开 2 层、间距 11 种——每一条都过门禁，合起来就是丑。

所以 `frontend-e2e` 那套二值门禁（有没有、是不是 token）**结构上抓不到丑**。
本 skill 补的是**程度**：不问对错，问多少。

| | 判什么 | 例 |
|---|---|---|
| `frontend-e2e` | 对/错 | 字段缺没缺、交互通不通、色值是不是 token |
| **`ui-review`（本 skill）** | 程度 | 字号几种、灰阶几层、多少元素真有动效 |

## 何时触发

- 用户说「丑 / 难看 / 没设计感 / 太平 / 像模板 / 有 AI 味」——**不要直接去改 CSS，先跑本流程**
- 重设计 / 视觉打磨开工前，先量现状（否则改完无法证明变好）
- 定期视觉巡检、多端风格一致性核对

## 三步流程

### 1. 计量（拿数字，不靠肉眼）

```bash
cs ui <url>                      # 判据 + 参考量
cs ui <url> --vs <baseline>      # 与参照站基线逐项对比
cs ui <url> --json               # 出 JSON，需要自己算的时候用
```

渲染后计量：打开页面遍历所有可见元素的 `computedStyle`，统计实际生效值。
输入只有 URL，**零项目知识**——React/Vue/Astro/纯 HTML 一视同仁，
所以能用同一把尺子量自己的页面和参照站。

> **实现在开源 npm 包 `contrast-guard`**（源码 `~/dev/agent-infra/contrast-guard`）。
> `cs ui` 只是薄封装，作用是把基线目录指到 CortexOS `var/ui-baselines`，让基线跨项目共享。
> 在没有 cs 的项目里直接用 `contrast-guard measure <url>`，参数完全一致。
> **判据和阈值只在 npm 包里维护一份**，不要在 cs 侧另写一套。

首次使用先建基线（**这一步别省，没有参照物就没有判据**）：

```bash
cs ui https://linear.app --save linear
cs ui https://vercel.com --save vercel
cs ui --baselines                # 看已存的
```

### 2. 看图（自研 MLX 本地视觉引擎自动挑刺）

```bash
# ① 浏览器截图（ego-browser，TaskSpace 隔离）
ego-browser nodejs -e '
const task = await taskSpace("ui-review");
const page = task.page("p1");
await page.goto("<url>");
await page.screenshot({ path: "/tmp/ui-review-screenshot.png" });
await task.finish({ keep: [] });
'

# ② 调用自研本地视觉引擎（mlx-vlm-kit / vlm）自动审查看图（零 API 成本）
vlm ask /tmp/ui-review-screenshot.png -q "以资深 UI 设计师视角审查此页面：1. 视觉焦点与留白是否协调？2. 元素排版与对齐是否存在瑕疵？3. 是否有截断、重叠或层级错乱？请列出具体修改点。"
```

计量抓不到的：视觉焦点在哪、留白节奏、对齐轴是否统一、元素比例是否协调。
**优先使用本地 `vlm` 自动看图挑刺**，配合人工审查，零成本压榨 Apple Silicon 算力。

### 3. 定位（每条都要能直接改）

产出格式固定为「成因 → 证据 → 位置 → 改成什么」：

```
⚠️ 层级压不住｜背景灰阶仅 2 层（参照站 22 层）
   位置：卡片区 .stat-card 与页面背景同为 #fff
   改为：卡片用 --mg-surface-2，页面底用 --mg-surface
```

**禁止**输出「建议优化视觉层次」「可以更精致一些」这类无法执行的话。
一条评审如果读完不知道改哪个文件的哪一行，这条就是废的。

## 判读指南：计量不是审美分数

字号、字体族、灰阶与动效覆盖率都是定位线索，没有跨产品通用及格线。阈值须来自项目契约、适用标准或同条件参考，注明用途、样本和失败影响。静态界面不因动效少判失败，多字体也可能是明确角色分工。先打开截图并追踪 token 与组件，再判断是否需要改动。

完整判定与覆盖矩阵以 [评审标准](../../docs/frontend-review-standard.md) 为准。历史参照站的数据不作为新项目默认门禁。

## 成因清单（对着截图逐条查）

静态视觉，丑几乎全部落在这九条里：

1. **层级压不住** —— 元素同权重，眼睛不知道看哪（查灰阶层数、字重跨度）
2. **灰阶不够** —— 只有黑白两级，缺中间层，画面显脏或显平
3. **留白不足** —— 密度过高，元素互相挤压（最高频）
4. **对齐轴太多** —— 左边界不齐，视觉散
5. **字号台阶太密** —— 16/17/18 这种，人眼分不出只感到乱（查集中度）
6. **圆角/阴影不统一** —— 同屏多套规格
7. **饱和度失控** —— 两个以上高饱和色抢戏
8. **边框滥用** —— 什么都描一圈线，该用背景色分层的地方用了边框
9. **比例失调** —— 图标、文字、按钮的大小关系随意

动效，丑的成因集中在六条：

1. **duration 一刀切** —— 小元素 100–150ms，中等 200–250ms，大面板 300–400ms；>400ms 一律拖沓
2. **用了 `ease` 或 `linear`** —— 物理世界快起慢停，进场 `ease-out`、退场 `ease-in`，位移大的用 `cubic-bezier(0.16,1,0.3,1)`
3. **只有进场没有退场** —— 元素消失时啪一下没了
4. **该连续的做成了离散** —— 拖拽/滑动等松手才动，必须 1:1 跟手
5. **动了不该动的** —— 装饰动画抢注意力；动效应解释状态变化，不是表演
6. **没做 `prefers-reduced-motion`**

## 风格画像：给基线补上计量抓不到的部分

数字回答「差多少」，画像回答「差在哪种气质」。基线 JSON 里的 `profile` 字段
（结构参考 mono-color-skill 的 `reference-analysis.json`）：

```json
{
  "profile": {
    "typography": ["hero 48px 与正文 14px，跨度 3.4 倍，中间几乎不落台阶"],
    "color": ["背景近黑但不纯黑（亮度 16），避免纯黑的廉价感"],
    "layout": ["hero 上方留约 200px 纯空白，不塞任何东西"],
    "motion": ["主力 duration 0.1s，比常见的 0.2-0.3s 快一档"],
    "signatureMoves": ["hover 响应 0.1s —— 快到几乎无感，是「跟手」而非「动画」"]
  }
}
```

**`signatureMoves` 是最重要的一项**——它是风格辨识度的来源。缺了它，评审只能说
「你灰阶不够」，说不出「你缺一个记忆点」。

填法：`cs ui <url> --save <name>` 存好数字后，**看截图**，把观察到的写进
`var/ui-baselines/<name>.json` 的 `profile`。重新计量不会覆盖已填的画像。
每条都要有具体数值或位置，不写「排版精致」这种。

## 与其它 skill 的关系

- `award-creative-ui` —— **国际获奖级研发与门禁**。提供短板一票否决律、实体触觉一致性标准与动效安全基线。
- `landing-page-design` —— **生成侧（唯一）**：落地页/营销页/产品 UI 的数值规范（字号阶梯、间距、圆角、六态、转化结构）。新建或重设计页面时加载它。
- `design-to-motion` —— **动效侧**：静态设计动起来并导出 MP4 / GIF。
- `frontend-e2e` —— **功能验收**（对/错）。两者在 `cs flow frontend` 第⑥步并列，都是硬门。
- `apple-design` —— 动效发现问题后，具体怎么改（弹簧、手势、可中断动画）查它。

## 创意任务的补充检查

针对创意主站、数字展厅或高定界面的评审，按项目适用范围检查以下 4 项**短板一票否决检查**：
1. **触控与手势等价性**：49 帧动效/Canvas 交互是否在触屏上支持 Touch Scrubbing？禁止鼠标指针特权。
2. **全键盘可操作性**：可交互卡片/按钮是否支持 Tab 导航并具备清晰高对比度的 `:focus-visible` 轮廓？禁止全局 `outline: none`。
3. **实体触觉一致性**：交互元素是否有 `:active` 物理下压（scale 0.96~0.99）？禁止没有按压反馈的“纸片悬浮”。
4. **前庭神经安全**：是否 100% 覆盖 `prefers-reduced-motion: reduce`？开启时必须停用持续无限自转与 3D 透视倾斜。

## 禁止项

- 禁止跳过计量直接凭截图下结论——「我觉得」不是判据
- 禁止跳过截图只读数字——留白、对齐、焦点数字抓不到
- 禁止输出无法执行的评审条目（见上文格式要求）
- 禁止在没有参照基线的情况下断言「这个数字偏高/偏低」
