# UI 评审规则的持续演进

持续改进指持续积累可复核的判断依据，不是持续改 CSS。每条规则先限定适用情境，再用正例与反例检验；只有证据支持时才推广。界面评审的执行方式见 [前端 UI 评审标准](frontend-review-standard.md)。

本机制管理审美假设、产品模式和 token/组件约束；外部可用性标准另记来源与版本，不通过局部审美试验放宽。维护规则时沿用已有正文真源，不复制一套会漂移的清单。本文件中的案例都是假设性示范，不是验证记录。

## 1. 规则有身份、版本与适用边界

每条规则使用永久 ID，例如 `UI-HIER-001`、`UI-TOKEN-001`；废弃 ID 不再分配。ID 表示一个可证伪主张，不把多种独立建议塞进同一条。不同主张创建新 ID 并记录继承关系。

规则版本使用 `major.minor.patch`：改变适用范围、判定或必需动作升 major；补充不改变判定的证据/例子升 minor；纠正文案与失效链接升 patch。规则集另有版本及包含的规则版本清单。每次评审固定所用版本；新版本不悄悄改写过去的结论。

```yaml
id: UI-HIER-001
version: 0.1.0
status: proposed
claim: 在以异常定位为主任务的概览中，异常信号应比辅助汇总更早被识别。
layer: contextual-aesthetic
scope: 异常监控概览；主任务为定位需要处理的异常
exclusions: 等权资产比较、财务对账、编辑阅读流
trigger: 辅助指标的视觉重量掩盖异常入口
rationale: 待验证的任务优先级假设
provenance:
  origin: 评审记录/原始截图或研究来源 ID，作者与日期
  environment: 产品与构建版本、数据 fixture、主题、视口、状态
  reference: 参考模式的来源/日期/可迁移点；无则注明缺失
positive_examples: [] # 每项含证据 ID、实际观察、适用原因
counterexamples: [] # 每项含证据 ID、失效条件、保留的不同做法
trial:
  hypothesis: 提升异常与时间范围的视觉层级，改善定位过程
  change: MetricSummary 组件层级；列出涉及 token 与受影响实例
  success: 事先定义的任务观察/对照判据，尚无验证结果
  guards: 可读性、键盘、数据真实性、其他主题与状态不退化
  budget: 本轮时间、候选数量、影响范围与停止条件
  rollback: 可恢复基线及触发条件
validation: [] # 区分自动检查、截图观察、任务验证和独立复核
owner: 维护角色或负责人
review_trigger: 新产品类型、反例、组件大改或约定复查日期
supersedes: null
superseded_by: null
```

字段是记录要求，不表示仓库已有自动执行器。状态与证据放在项目既有评审记录中；只在授权的文件范围维护，不擅自新增流水线、发布或外发记录。

## 2. 四阶段生命周期

| 状态 | 进入依据 | 能做什么 | 离开条件 |
|---|---|---|---|
| `proposed` 提议 | 有可定位观察、任务影响假设、适用范围与反驳条件 | 提出局部改进，列未知项；不作为普遍发布门禁 | 试验计划、基线、预算和保护条件完整后进入 trial；重复、无依据或已被推翻则 deprecated。 |
| `trial` 试行 | 固定版本与基线，有受限改动和可复现比较方法 | 在声明的产品/组件内验证；每轮记录结果及反例 | 支持证据充分则 stable；结果混合时缩窄范围并发新版本；保护条件失败则回滚，证据不足则停止并保留未决状态。 |
| `stable` 稳定 | 原始证据可追溯，正例与反例已检查，适用范围内重复验证并有独立复核 | 作为声明范围内的评审依据，仍可被反例挑战 | 新证据冲突时重新 trial，或由替代规则接续并 deprecated。 |
| `deprecated` 退役 | 被推翻、被更具体规则替代、成本高于收益或范围失效 | 保留版本、证据、原因与替代路径供追溯；退出活动门禁 | 重新研究时建立关联的新版本/主张，不删除历史来伪造连续成功。 |

Stable 的证据量取决于主张覆盖面和变更风险：单一组件规则至少要有同条件可复现对照、实际检查的完整覆盖及另一位评审者复核；跨产品主张还要在不同任务与内容中检验边界。正例数量本身不构成稳定依据。单人或单 Agent 暂无独立复核时保留 trial，注明限制，不以“我再次看过”替代独立性。

## 3. 正例与反例同等重要

每条规则同时维护两类材料：

- **正例**：记录规则在哪个任务、内容、主题、视口与状态成立；包含原始截图/交互证据、实际观察及影响依据，而非只有精选展示图。
- **反例**：主动寻找规则不适用或会损害体验的情况。记录触发边界与应保留的不同做法；反例可促成缩窄范围、改写主张或退役。尚未找到反例时写出检索范围和待验证的反例候选，不把空列表当作普适证明。

素材来源记录作者/产品、日期、可访问位置、构建与数据条件、观察方式；引用外部模式要能追到原始页面或截图。历史截图与当前实现分开，竞品宣传图与真实任务证据分开，模拟用户推断与真实用户观察分开。失效链接要保留可核验的归档说明或降低证据置信度。

示例证据条目可写：`E-17：构建 X，dark，窄屏，长包名；检查了标题和命令区，命令可完整访问；任务耗时未测，效率改善仍是假设。` 不写“更好看了，规则成功”。

Agent 的完成声明、模型打分、自动截图成功、生成者的自我表扬、工具无报错、一次点击通过，都不是规则有效的独立证明。自动检查只能证明其断言覆盖部分；截图须由评审者实际打开并写出观察；效率、理解或满意度的因果主张需要相应任务研究，不能仅从截图推导。保留原始记录、失败样本和相互矛盾的结果。

## 4. 从一次发现到一次受控试验

1. **观察**：固定构建、数据及 [评审矩阵](frontend-review-standard.md#5-明确覆盖矩阵并真正检查截图)，采集并实际检查改动前证据。查现有规则，先更新相关条目，避免重复规则。
2. **影响**：写明受影响用户与任务，区分已观察问题与尚待验证影响。严重问题先恢复可用性，审美提议另行检验。
3. **假设**：说明预计改善的可观察结果、替代解释、反例候选和推翻条件。事先确定成功判据，避免看到结果后移动目标。
4. **Token/组件改动**：优先最小范围，列出语义角色、组件实例、主题和状态的传播范围；每轮只检验一个主要解释，其他必要变更单独记录。
5. **验证与保护**：同条件对照，复跑受影响的自动检查，实际检查截图与交互；任务表现另用相应方法验证。保护可读性、键盘与焦点、减弱动效、数据诚实、性能、品牌及未改动的关键任务。
6. **决定与归档**：保留、缩窄、继续试行或回滚；写出支持与反对证据、未验证范围、复核者和下一次触发条件。只有获证据支持的结论进入稳定规则。

自动化适合检查确定性断言、token 引用和覆盖缺口；它可提出审美候选，不能自行把候选升级为“美”的真理。任何自动修改规则或扩大门禁的提议，仍走同样的版本、对照与复核过程。

## 5. 变化预算、停止与回滚

试验前写下项目自己的预算：时间盒、候选方案数、迭代轮数、允许修改的 token/组件、影响页面和验证成本。预算由任务风险、范围与交付约束决定，不设全项目通用数字；“一直改到好看”不算预算。全局 token 改动扩大验证范围时重新核算预算，不沿用局部组件试验的额度。

**停止条件需预先声明：**

- 成功判据已满足且保护条件通过：停止追加打磨，记录保留决定；进入 stable 仍需生命周期要求的证据与复核。
- 连续对照未出现可辨认的收益，变化仅在互换偏好：按预定观察窗口判断边际收益递减，停止；保留证据更强或变更更少的版本。
- 时间、候选或变更范围预算耗尽：停止扩大范围，记录未决项与重启所需的新证据。
- 关键主题/视口/状态缺证据、数据条件改变或结论冲突：暂停推广，不追加无依据的通过声明；明确保留 trial 的范围与期限。

**回滚条件需绑定可恢复基线：**

- 任一关键保护条件退化，例如对比度失效、焦点丢失、主要操作被遮挡、窄屏丢失领域对象、信息被误导或性能超出项目预算。
- 主要假设被对照推翻，或收益只在精选截图成立而真实状态退化。
- 实际影响超出授权/预算范围，或全局 token 改动的回归成本超过预期收益。

记录恢复的构建/改动标识、token/组件原值和 fixture；回滚只撤销该试验的变更，保留其他人的修改。恢复后复验原问题和保护条件。旧规则的 HOLD 不靠降低门槛清除，应记录修复、范围收缩或规则失效的证据。暂停与回滚都属于有效学习结果，不包装成成功案例。

## 6. 三个规则演进示例

以下状态均为 `proposed`，需要真实证据才能试行或升级。

| 规则 ID 与主张 | 正例候选与反例候选 | 试验、保护与停止 |
|---|---|---|
| `UI-DIR-001@0.1.0`：CLI 目录的比较列表应保持工具身份、用途和安装入口的邻近关系。 | 正例候选：开发者连续比较多个相似工具，紧凑行可同时显示关键差异。反例候选：教程型目录需展示预览与长解释，强压一行损害理解。 | 局部改 `ToolRow` 的文字/代码角色与间距；比较搜索定位及复制路径，检查长名称、空态、错误、焦点与两主题。若仅减少高度却降低命令可访问性则回滚；预算耗尽仍无比较收益则停止。 |
| `UI-DASH-001@0.1.0`：异常监控概览优先呈现异常及比较周期。 | 正例候选：运营先定位异常再钻取原因。反例候选：对账人员必须等权核对所有账目，过度突出一个 KPI 会误导。 | 试 `MetricSummary` 层级与状态色映射；用同一数据检查异常定位并保留尺度、单位及来源。无数据态不得伪造趋势；若定位收益不明确，保留 trial；其他指标比较受损则回滚。 |
| `UI-EDIT-001@0.1.0`：长文阅读的章节节奏应保持连续阅读与导航。 | 正例候选：正文、图注与章节间距表达稳定角色。反例候选：实验诗歌、视觉报道以非常规断裂承载内容，统一节奏会抹去编辑意图。 | 局部试正文/标题/图注 token 与图像位置；实际检查长题、图片失败、两主题、窄屏和放大，并按需做阅读任务观察。避免引入额外动效；若变化只反映字体偏好且无任务收益，按预算停止。 |

## 7. 每轮最小交接记录

```text
规则集版本 / 规则 ID@版本 / 状态：
范围与产品契约：
原始证据及来源（正例 + 反例）：
观察→影响→假设→token/组件改动→验证：
主题×视口×状态结果与实际截图检查者：
支持证据 / 冲突证据 / 未知项：
预算消耗 / 边际收益 / 保护条件：
决定：保留、继续 trial、缩窄范围、回滚或 deprecated。
复核者 / 恢复基线 / 下次复查触发条件：
```

复查由新反例、产品任务变化、主题或组件大改、真实用户反馈及约定日期触发。复查时合并重复规则、收缩过宽主张、清理失效证据并保留退役路径；规则数量增长不作为系统改善指标。
