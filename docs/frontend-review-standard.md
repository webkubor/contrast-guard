# 前端 UI 评审标准

本标准用于人和 Agent 评审真实界面：先确认产品任务，再检查可用性、设计 token 与视觉表达，最后用证据判断是否值得改动。目标是让界面好看、可信、适合其产品，而不是让所有页面收敛成同一套模板。

contrast-guard 提供配色检查与渲染后计量；这些结果是评审证据的一部分，不代表完整无障碍验收或审美结论。规则如何更新、试验和退役，见 [规则演进](rule-evolution.md)。本标准不替代项目自己的产品契约和适用的无障碍标准。

## 1. 三层评审，分别给结论

| 层次 | 核心问题 | 证据与边界 |
|---|---|---|
| 自动化可用性检查 | 用户是否看得清、操作得到、完成任务？ | 配色对比度、溢出、遮挡、焦点可见性、交互与路由检查。脚本通过仅说明已检查断言成立；键盘流程、语义、读屏等还需相应人工验证。 |
| Token 完整性 | 同一语义是否由同一套设计决策控制？ | token 定义与引用、组件变体、运行时 computed style、主题映射。统计可定位异常，定义与来源追踪才能证明是否绕过体系。 |
| 情境化审美评审 | 信息层级、节奏、构图与表达是否服务这个产品？ | 实际检查过的截图、产品契约、真实内容、交互观察及相关参考。明确评价理由、替代假设与取舍。 |

三层分别记录 `PASS / HOLD / 未验证`。阻断任务的缺陷、关键覆盖缺口与契约冲突进入 HOLD；偏好性打磨另列，不伪装成发布阻断。局部通过不外推为整站通过。总门禁仅在声明范围内必需证据齐全且关键问题关闭时为 PASS。

计量值用于发现问题，不把任意分布当作美的代理指标：动效覆盖率、字体族数、字号集中度、灰阶数量、圆角种类与卡片列数均无跨产品通用及格线。特定阈值须注明来源、适用条件和失败影响；WCAG 等外部标准须注明版本、等级与适用对象。

## 2. 改动前写产品设计契约

每个核心页面或工作流先填写以下契约。资料不足时标记假设及其验证方式；推断不写成用户研究事实。

```text
用户与任务：谁在什么环境完成什么工作？
首读对象：首先应识别的领域对象、状态或决策是什么？
主操作与成功条件：用户如何完成工作，怎样观察完成？
高频与高风险：重复操作、错误代价、恢复路径分别是什么？
密度与层级：紧凑/均衡/疏朗的理由；主信号、控制、辅助信息的顺序。
版式与交互模型：列表/表格/编辑器/时间线/阅读流等为何适用？
视觉身份：品牌语气、字体角色、色彩语义、图像/数据表达及辨识点。
约束：现有组件与 token、性能、语言、数据规模、无障碍与设备需求。
响应式优先级：窄屏保留什么，哪些折叠、重排或进入详情？
参考与禁用默认：参考模式→可迁移经验；本产品不适合的模板及理由。
验收范围：主题×视口×状态矩阵、证据与交互验证方式。
```

需要比较设计方向时，收集 3–5 个真实相邻产品的相关模式，注明来源、日期、任务与可迁移点；保留不适用的差异。参考是模式证据，不是复制整页的许可，也不是“某知名网站这样做”的通用判据。例行小修可以复用仍有效的参考集；缺失或过期处明确标记。

## 3. 审美检查要落到具体设计决策

按产品可读性、信息层级、模式适配、状态、响应式、实现一致性的顺序检查。每项既记问题，也记值得保留的选择。

| 维度 | 观察什么 | 可执行的改善方向与保护条件 |
|---|---|---|
| 字体与层级 | 标题、正文、标签、数字、代码的角色是否可辨；长标题、中文/拉丁文混排、字重与行长是否支持阅读？ | 按角色调整字号、行高、字重、行长和换行策略；数字比较可试等宽数字。字体数量由角色与加载成本解释，层级也可由位置与留白建立；保留缩放、字体回退与多语言可读性。 |
| 对齐、邻近与间距节奏 | 相关信息是否成组；标签与值是否比无关区域更接近；基线和重复行是否稳定？ | 在组件内收敛间距 token 和对齐锚点，调整组内/组间关系。允许图标等光学校正并记理由；别为追求数学等距破坏感知分组。 |
| 密度 | 用户是在扫描比较、连续操作还是沉浸阅读；留白是否挤走关键数据，压缩是否增加误触？ | 按任务调整行密度、详情层级和渐进披露。以真实数据量和工作流验证，不把空旷或紧凑当作天然高级。 |
| 构图 | 首读焦点是否明确；视觉重量、留白、比例、重复与变化是否形成有意的节奏？ | 提升关键趋势或领域对象，降级辅助模块；选择表格、列表或自由构图的理由来自内容。列数随信息与可用空间变化；避免等权卡片掩盖决策优先级。 |
| 色彩语义 | 文本、背景、边界、操作、状态与数据类别的颜色是否各司其职；强调是否被稀释？ | 用语义 token 表达 text/surface/border/action/status/data 等角色；分别校验主题和叠加后的实际配色。状态附带文字或形状；装饰色不抢占风险信号，数据色不暗示虚假顺序。 |
| 产品特色与交互 | 控件是否贴合领域任务；反馈是否解释实际变化；用户能否撤销、恢复和继续？ | 让特色出现在真实操作中，如命令复制、时间范围对比、阅读导航。复用成熟组件并调整领域变体。动效只用于反馈、连续性或解释变化；记录目的，测试 reduced-motion 与键盘等价路径。静态界面可以完整成立。 |
| 图像与诚实内容 | 图片、图表、文案是否承载信息；示例、占位与真实结果是否可区分？ | 选择与任务相关的素材并校验裁切、替代文本、来源及加载失败态。保留真实长短内容、单位、时间范围与数据来源；演示数据明确标注，零值、无数据和加载中分别表达。避免虚构评价、客户标识、性能或成效。 |

“更精致”“不够现代”“有 AI 味”只能作为调查入口。评审应继续说明：哪个可见关系失衡、影响哪个任务、为何选择这个方向，以及什么证据会推翻判断。简洁界面无需靠装饰证明设计投入。

## 4. Token 是决策系统，不是数值去重表

- 区分基础值、语义别名和组件 token；追踪“组件→语义→基础值”的来源。类型、命名和层级沿用项目体系，不为统一命名另建并行系统。
- 颜色、字体角色、间距、尺寸、圆角、阴影、层级与必要的动效参数应有明确归属。同一角色漂移优先修组件或语义映射，避免逐个页面打补丁。
- 浅色与深色主题共享语义目的，各自映射可读的值；深色主题无需机械反转。对比度同时考虑透明度、背景叠加、交互状态和实际渲染。
- 数值多不自动意味着失控：图片、图表、抗锯齿和第三方内容会增加颜色数量。数值少也不证明语义完整。孤立硬编码先查来源，必要例外记录用途、范围、负责人及复查条件。
- token 调整须列出受影响组件、主题与状态；全局 token 的收益和回归范围一起验证。OKLCH 修复保留精度；对比度失败应给出可行修复值或明确约束冲突，不能只报一个失败数值。

## 5. 明确覆盖矩阵，并真正检查截图

评审范围必须展开为 **浅色/深色 × 视口 × 状态** 的显式矩阵。主题不支持时标 `不适用` 并说明产品依据，不冒充已测。视口依据支持设备、真实窗口和断点选择，至少覆盖适用的窄屏与桌面，并检查发生布局变化的临界宽度及分屏环境；记录实际宽高与缩放。没有统一强制列数、文本最小宽度或浮层高度。

状态按工作流列出：正常、加载、空、失败/恢复、超长/极值内容、选择、焦点、禁用、无权限，以及适用的展开/弹层状态。每个组合有结果；可用等价类减少重复执行，但须写清代表项、等价依据和未直接验证范围。高风险交互与发生主题/布局变化的组合直接验证，不凭等价推断。

| 页面/版本 | 主题 | 实际视口/缩放 | 状态与数据 fixture | 截图/交互证据 | 检查者与实际观察 | 结果/缺口 |
|---|---|---|---|---|---|---|
| 待填写 | light / dark | 宽×高 / 比例 | 可复现输入 | 路径或证据 ID | 已打开检查的具体区域 | PASS / HOLD / 未验证 / 不适用及理由 |

执行时：

1. 固定版本、数据、主题与页面状态，记录环境；先建立改动前证据。
2. 在真实运行页面触发主要动作、弹窗、抽屉与恢复路径；检查焦点、键盘顺序、内容遮挡、溢出和操作结果。表格或画布需要局部横向滚动时，说明操作和可发现性，避免无意义的全页溢出。
3. 生成全页与必要局部截图后，**逐张打开并实际检查**。记录观察区域与发现；截图文件存在、工具返回成功、DOM 指标正常都不等于已检查视觉。
4. 同条件对比改动前后，补查长内容、临界断点、主题和受影响组件。动画时序与交互行为使用实际操作或录制证据，静态截图只证明捕获时刻。
5. 给每层结论附证据和局限。没有运行环境或未打开截图时记“未验证”，不生成审美分数或通过声明。

禁止无证据打分。需要量化时先定义量表、样本、分母、对照、评价者和不确定性；分数不替代具体发现，也不把一个视口的好看外推到整站。

## 6. 每条改进采用可证伪闭环

```text
发现 ID / 范围 / 规则版本：
观察：证据 ID + 主题/视口/状态 + 可见事实（与解释分开）。
影响：谁的哪一步受影响，严重程度与依据；未知影响标为假设。
假设：改动预计改变什么；替代解释是什么；何种结果会推翻它？
Token/组件改动：具体角色、组件变体或布局调整；例外及影响范围。
验证：相同条件前后对照 + 可观察成功条件 + 已检查截图/任务结果。
保护条件：可读性、任务完成、键盘/减弱动效、性能、品牌及其他主题不退化。
结论：保留/继续试验/回滚；残余风险、置信依据与未验证范围。
```

修复优先级按任务阻断、误导风险、频率和影响范围确定；审美偏好与已观察的可用性失败分开。先处理根因，优先最小 token/组件改动，避免用一轮全面换肤同时试验多个解释。变化预算与停止条件按 [规则演进](rule-evolution.md) 执行。

## 7. 三个紧凑示例（假设性方案，不是已验证结果）

| 产品契约 | 观察→影响→假设 | 改动→验证与保护条件 |
|---|---|---|
| CLI 目录：开发者搜索、比较并复制安装命令；首读是工具名与用途，紧凑列表优先。 | 等权大卡片把名称、用途与命令分散，比较路径变长；假设同行组织可减少回看。 | 调整 `ToolRow` 的标题/元信息/代码角色与组间距，加入真实复制反馈；在两主题、窄屏/分屏/桌面验证搜索空态、长包名、复制失败和键盘操作。保留命令完整可访问与真实包来源；不强制卡片列数。 |
| Dashboard：运营判断异常并定位原因；首读是异常趋势及比较周期。 | 四个同重 KPI 抢占异常图的焦点；假设提升异常与时间上下文能改善定位。 | 调整 `MetricSummary` 层级，次级指标收为辅助行，状态色走语义 token；用相同数据比较定位异常的过程，检查加载、无数据、错误和窄屏筛选。保留单位、图表尺度、数据来源及非颜色编码。 |
| 编辑型站点：读者选择文章并持续阅读；首读是标题、摘要与作者信息。 | 频繁边框和插图打断段落，标题装饰挤压长题；假设稳定阅读列和章节节奏能改善连续阅读。 | 调整正文/标题/图注角色、段间距和图像裁切；两主题检查长题、正文、图片失败、放大与窄屏。保留编辑语气、作者署名和真实引文；不因稀疏动效或多字体角色判失败。 |
